# Optional account server (rfe-7np)

Decision (owner): offer an option to host an account server; do not delete login/register.

Design: any agent can opt in (default off) to an account-server role with its own Ed25519 signing key. It signs short-lived (<=5 min) login assertions {iss, sub username, aud member cert fingerprint, devicePublicKey, nonce, exp}. Member agents pin the server's key once (owner action, fingerprint compared, like pairing) and accept an assertion at POST /v1/login as an alternative to password. The device-key proof and single-use nonce stay required. Federated logins mint a viaLogin token (owner) through a new store.LoginDeviceFederated. Passwords never leave the account server. Rejected: password forwarding to the server (members see plaintext), copying hashes to members, a separate binary.

Phases: 1 agent (key, GET /v1/accounts/key, POST /v1/accounts/assertion, rfe accounts trust/untrust/status, login assertion branch, health accountServer field, openapi); 2 mobile (agentClient calls, 'Sign in with account server'); 3 desktop Settings toggle and trust action; 4 revocation spreading and grant profile.
Open: federated logins as owner vs grant profile; revocation propagation; key separate from TLS key (recommended). Needs a security-engineer review before release.

## Security review 2026-11-15

Review of phase 1 to 3 (agent, mobile, desktop). Findings and what this change does about each:

- F1 (fixed): untrusting the account server, or re-pinning a different key, revoked the federated sessions but left the share links they had minted, which kept serving files. Both store operations now delete those links in the same transaction as the revoke, over exactly the devices being revoked (re-pinning the same key touches nothing). Serving a link already refused one whose minting device is missing or revoked; a test now pins that.
- F2 (interim hardening, fixed): a session whose device carries a login issuer gets 403 FORBIDDEN on pairing-code generation, pairing-request list/approve/reject, PATCH and DELETE on /devices, PATCH /settings, user list/delete, and PUT/DELETE /settings/account-server (one helper, forbidFederated, applied as route middleware). Federated sessions keep browse/download/upload/modify/delete/share per their grants. Documented in protocol/openapi.yaml.
- F3 (fixed): POST /accounts/assertion now requires devicePublicKey to equal the calling device's pinned key (constant-time compare of the decoded bytes); a device with no pinned key gets 403.
- F5 (fixed): `rfe accounts trust --yes` now requires `--fingerprint <hex>` (case, colons, spaces and dashes ignored) and refuses, changing nothing, on a mismatch. Without `--yes` the interactive confirmation is unchanged.
- F6 (fixed): a rejected federated device proof (bad signature, replayed or expired nonce, key mismatch) writes a login_failed audit row, and federated audit actors are `<sub>@<first 12 hex of the issuer fingerprint>`.
- F4 (fixed): a federated session now expires 10 minutes (store.FederatedSessionTTL, a constant; was 24 hours) after the assertion that created or last renewed it. Migration 11 adds devices.federated_login_at, set by every federated login; DeviceByToken accepts a federated device only while that time is younger than the TTL, and a NULL time (a session minted before the migration) counts as expired. The first request with an expired token gets the normal 401, revokes the device, deletes its share links and writes one federated_session_expired audit row; a fresh assertion renews the same device.
- F7 (fixed): `rfe accounts rotate-key` writes a new Ed25519 key beside agent.db (mode 0600, temp file renamed over the old one), keeps the role's enabled state and name, audits the rotation and prints the new fingerprint with a warning that every member must re-pin it with `rfe accounts trust` (which ends that member's sessions from this server). CLI only; no API change.
- Epoch (fixed): the issuer keeps a monotonic `account_epoch` (migration 12), raised on user delete, device revoke and `rfe accounts revoke-all`, and carried in the signed assertion (`Epoch` claim). A member stores the highest epoch seen per issuer (`trusted_account_server.highest_epoch`) and the epoch each federated device was minted under (`devices.federated_epoch`). A higher epoch revokes every lower-epoch federated device and its share links; a lower epoch gets 401. The assertion endpoint refuses accounts that no longer exist.
- Grant profile (fixed): a federated device is never admin or owner. It gets `store.FederatedGrantProfile()`: browse, download, upload; no modify, delete or share. Migration 12 moves sessions minted earlier onto this profile and drops their share links. `denyFederated` stays as defence in depth.
- Still open: push revocation over SSE, fail-closed when the issuer is unreachable for about 30 minutes, client auto-renewal of the 10-minute session.
